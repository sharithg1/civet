# Releasing Civet

A release is a `vX.Y.Z` tag on `main`. Pushing the tag runs
`.github/workflows/release.yml`, which publishes a GitHub Release with:

| Asset | What |
|---|---|
| `Civet_X.Y.Z_macos-aarch64.dmg`, `…_macos-aarch64.app.zip` | Desktop app for Apple Silicon |
| `Civet_X.Y.Z_macos-x86_64.dmg`, `…_macos-x86_64.app.zip` | Desktop app for Intel Macs |
| `civetd-x86_64-unknown-linux-musl`, `civetd-aarch64-unknown-linux-musl` | Static daemons for Linux hosts |
| `civetd-aarch64-apple-darwin`, `civetd-x86_64-apple-darwin` | Daemons for macOS hosts |
| `Civet_X.Y.Z_macos-{aarch64,x86_64}.app.tar.gz`, `latest.json` | In-app update bundles and their manifest (see [In-app updates](#in-app-updates)) |
| `SHA256SUMS` | SHA-256 of every asset (`shasum -a 256 -c SHA256SUMS --ignore-missing`) |

Release notes are generated by GitHub from the merged PRs and commits since
the previous tag; edit them on the release page afterwards if needed.

## Cutting a release

**From GitHub:** Actions → **Cut release** → Run workflow (on `main`), enter
the version (`0.1.5`; tick "Dry run" to only see the bump). It runs
`scripts/release.sh` on `main`, pushes the "Release vX.Y.Z" commit and the
tag, and starts the Release workflow on the tag (a tag pushed by a workflow
does not trigger `push: tags` itself, so it is dispatched explicitly). If
`main` gets branch protection that blocks pushes from Actions, this needs a
bypass for the workflow or a personal token instead of `GITHUB_TOKEN`.

**From a laptop**, on an up-to-date, clean `main` with green CI:

```sh
scripts/release.sh 0.1.5 --dry-run   # show what changes, touch nothing
scripts/release.sh 0.1.5             # bump, commit "Release v0.1.5", tag v0.1.5
git push --atomic origin main v0.1.5 # the script prints this; it never pushes
```

`scripts/release.sh` sets the version in the root `Cargo.toml`
(`[workspace.package]`, inherited by every crate including `civetd`) and in
`crates/civet-desktop/tauri.conf.json`, refreshes `Cargo.lock`, commits and
creates an annotated tag. It refuses a version that is not newer than the
current one (features are gated on each side's version, so going backwards
turns them off), a dirty tree, a branch other than
`main` (unless `--allow-branch`), an existing tag, or a `main` behind
`origin/main`. To undo before pushing: `git tag -d v0.1.5 && git reset --hard HEAD~1`.
(`crates/civet-desktop/ui/package.json` has its own unused `0.1.0`; it is not
part of the release version.)

The workflow then:

1. **version**: `scripts/check-version.sh vX.Y.Z` fails the run unless the
   tag, `Cargo.toml` and `tauri.conf.json` all say `X.Y.Z`, and decides the
   signing policy (see [Signing and notarization](#signing-and-notarization)).
2. **CI**: the whole CI workflow (`ci.yml`, called as a reusable workflow)
   on the release commit. A tag, or a commit pushed by Cut release, does not
   trigger CI by itself, so this is the only CI run that commit gets;
   nothing is published unless it passes.
3. **daemons**: one job per `civetd` target, in parallel (Linux musl on
   Ubuntu via `cargo-zigbuild`, macOS on a macOS runner), each running
   `scripts/build-remote.sh` (`dist` profile, `--locked`) and checking the
   binary's embedded version marker.
4. **app** (aarch64 and x86_64, both cross-built on an Apple Silicon runner):
   copies the two Linux daemons and the matching Mac daemon from step 3 into
   `crates/civet-desktop/civet-dist`, then `CIVET_SKIP_DAEMONS=1 pnpm tauri
   build --target <triple> --bundles app,dmg`. Because the bundled daemons are
   the files from step 3, they are the release version: the app refuses a
   `civetd` from another version ("is civetd 0.1.3, expected 0.1.4"). The job
   checks the bundled daemons' versions, `Info.plist` and the signature. With
   the updater key it also signs `Civet.app.tar.gz` for in-app updates.
5. **publish**: writes `latest.json` and `SHA256SUMS`, uploads everything into a **draft**
   release (`--generate-notes`), downloads the draft's assets back and
   compares their checksums, then publishes the draft. Tags with a suffix
   (`v0.2.0-rc.1`) become pre-releases. Re-running a failed run replaces an
   unpublished draft, but never touches a published release: its assets are
   what users downloaded. To replace a published release, delete it on
   GitHub first (or, better, cut a new version).

Builds are reproducible from the tag: Rust is pinned by `rust-toolchain.toml`,
`cargo-zigbuild` and zig by version in `release.yml`, and every build uses
the committed `Cargo.lock` (`--locked`, or `cargo fetch --locked` before
`tauri build`). Bump the toolchain in its own PR so CI checks it.

Pull requests that change `release.yml`, `scripts/build-remote.sh`,
`scripts/check-version.sh` or `tauri.conf.json`, and manual runs on a branch
(Actions → Release → Run workflow), do steps 1–3 without publishing (a
manual run on a tag publishes, which is how Cut release starts it); the app and daemon
builds are kept as workflow artifacts.

If the tag check or CI fails (tagged the wrong commit, forgot the bump, a
broken test): delete the tag locally and on GitHub
(`git push origin :refs/tags/vX.Y.Z`), fix, and tag again.

## Signing and notarization

**Policy.** A stable tag (`vX.Y.Z`, no suffix) must be signed with a
Developer ID and notarized: the run fails before publishing if any of the
six secrets below is missing. Pre-release tags (`v0.2.0-rc.1`), pull
requests and branch runs sign when the secrets exist and fall back to an
ad-hoc signature otherwise. To publish unsigned stable releases on purpose
(no Apple Developer account yet), set the repository **variable**
`ALLOW_UNSIGNED_RELEASES` to `true` (Settings → Secrets and variables →
Actions → Variables); the run summary then says "signing: optional".

With an ad-hoc signature (`APPLE_SIGNING_IDENTITY=-`) the bundle is sealed
but not from an identified developer, so macOS blocks the downloaded app
("cannot be opened" / "is damaged"). Users clear the quarantine flag once
after installing:

```sh
xattr -dr com.apple.quarantine /Applications/Civet.app
```

(or right-click → Open, or System Settings → Privacy & Security → Open
Anyway, depending on the macOS version). The standalone `civetd` downloads
are not affected when fetched with `curl`/`wget`; if downloaded with a
browser, run `xattr -d com.apple.quarantine civetd-*-apple-darwin`.

Repository secrets (Settings → Secrets and variables → Actions):

| Secret | Value |
|---|---|
| `APPLE_CERTIFICATE` | base64 of the "Developer ID Application" certificate + key exported as `.p12` (`base64 -i cert.p12 \| pbcopy`) |
| `APPLE_CERTIFICATE_PASSWORD` | the `.p12` export password |
| `APPLE_SIGNING_IDENTITY` | e.g. `Developer ID Application: Your Name (TEAMID)` |
| `APPLE_ID` | Apple ID email used for notarization |
| `APPLE_PASSWORD` | an app-specific password for that Apple ID |
| `APPLE_TEAM_ID` | the 10-character team ID |

With the first three the app (and the Mac daemons, with the hardened runtime
and a timestamp) are signed; with all six Tauri also notarizes and staples
the app. The run summary says which mode was used. The signed path has not
been exercised yet: check the first signed release with
`spctl -a -vv /Applications/Civet.app` and
`codesign -dv --verbose=4 /Applications/Civet.app`.

## In-app updates

The app checks
`https://github.com/sharithg1/civet/releases/latest/download/latest.json`
(`plugins.updater` in `tauri.conf.json`) 20 s after launch and every 6 hours,
and from **Civet → Check for Updates…** / the About window. A newer version is
downloaded in the background and verified against the updater public key
(also in `tauri.conf.json`), then the status bar shows **Restart to update**:
that swaps the `.app` in place and relaunches. Daemons and their panes keep
running across the restart, as on any quit; a host whose daemon is older then
shows the usual "civetd vX available" hint. Pre-releases are never offered
(`releases/latest` skips them). Debug builds and `CIVET_NO_UPDATE_CHECK=1`
skip the periodic check.

The update bundles are signed with a minisign key separate from Apple's:

| Secret | Value |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | contents of the private key file (`pnpm tauri signer generate -w ~/.tauri/civet-updater.key`) |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | its password |

Tag runs fail without them. **Keep a backup of the private key**: installed
apps only accept updates signed by it, so losing it means users must
reinstall by hand once a new key ships. Rotating the key takes two releases:
one signed with the old key that carries the new public key, then the rest.

`tauri-plugin-updater` depends on `zip` 4 on Windows only, and every `zip`
4.x release is yanked; `Cargo.lock` pins the yanked 4.6.1 (never built for
macOS), which `--locked` builds accept. A full `cargo update` fails until the
plugin moves to a newer `zip`; update other crates with `cargo update -p <crate>`.

## Building release artifacts locally

```sh
cd crates/civet-desktop/ui && pnpm install
pnpm tauri build --bundles app,dmg                              # this Mac's arch
pnpm tauri build --target x86_64-apple-darwin --bundles app,dmg # Intel (rustup target add x86_64-apple-darwin)
```

`beforeBuildCommand` runs `scripts/build-remote.sh --bundle`, which builds the
Linux daemons and the daemon for the target Mac (from Tauri's
`TAURI_ENV_TARGET_TRIPLE`). Output is under `target/release/bundle/`
(`target/<triple>/release/bundle/` with `--target`).
